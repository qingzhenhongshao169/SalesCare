# SalesCare 下一轮调优总方案

版本：2026-10-15 / v1。状态：**待实施方案**，不是已完成能力说明。本轮仅整理文档，不变更运行中的代码、数据或配置。

## 一、核心目标与执行优先级

下一轮以「理解用户 → 正确更新需求 → 基于同一需求回答和接待」为主线。用户体验目标是：能听懂自然更正与省略，记住本次咨询，不把猜测写成事实，不反复索取已说明的信息，并保持现有快速回复体验。

产品仍是面向多企业的 SaaS。标梵是首个验收场景，通用底座不能写死为网站建设销售；购物、售后等企业通过受控业务模板配置字段和规则。

| 优先级 | 工作项 | 本轮交付 | 依赖/处理原则 |
|---|---|---|---|
| P0 | 统一需求状态、证据与更新规则 | 对话、画像、摘要和人工交接读取一致版本；明确更正、暂定、区间、取消、冲突 | 先解决数据语义，不继续以补关键词作为主体方案 |
| P0 | 多意图语义理解 | 结构化识别意图、对象、字段变更与待澄清项 | 使用企业现有模型接入；模型结果不能未经验证直接写库 |
| P0 | 回答与接待联动 | 按最新需求回答、合理澄清、识别人工协助意图；不改变人工接管规则 | 画像更新不能授权报价、履约或人工动作 |
| P0 | 评测、延迟和故障控制 | 多轮正确性、误覆盖、全链路延迟、模型失败分别验收 | 不用模拟模型速度替代真实模型或质量评测 |
| P1 | 企业业务模板与运营可见性 | 基础字段+租户业务字段；候选/暂定/冲突可见；错误可追溯、可纠正 | 先做一个最小通用模板和标梵模板，不做任意代码执行平台 |
| 后续 | 实时订单工具、长期记忆、独立备用模型、大规模检索、公网平台实测 | 本轮保留接口与边界，独立立项验收 | 不把所有基础设施需求并入本次重构 |

## 二、已完成基线与当前缺口

### 已完成并应保留

- PostgreSQL 多租户与权限控制、知识版本与来源核验、公开/内部及渠道范围隔离。
- 标准 FAQ 快答、任务提交唤醒、验证后消息推送与断线续接、企业隔离的模型连接池。
- 等候人工时 AI 继续服务，顾问接管后停止 AI 自主投递；原联系时限与审计不变。
- 预算自然表达补丁：已统一部分预算/时间解析，支持常见 5k/5000元表达。

### 未解决的结构性缺口

1. 画像主要依赖规则，LLM 主要生成回答，模型的语义理解没有形成经验证的结构化状态变更。
2. 持久化画像和回答历史解析仍各有状态；话题切换后可能出现一边清除、一边保留。
3. `confirmed=True` 没有充分区分「用户确实说过」「用户已确定」「企业已确认可交付」。
4. 单一 scene 不足以表示一条消息同时更正预算、询问分阶段实施和保留交期。
5. 缺少项目/商品等对象范围、完整变更历史、暂定/区间/冲突表达，以及稳定的澄清状态。
6. 通用客服需求容易被最新一句话覆盖，网站销售的固定字段又不能直接通用于所有行业。

当前证据：[预算补丁验收](预算更新-修复与验收-20261015.md)、[响应速度验收](两秒响应-实施与验收-20261015.md)、[知识底座验收](知识与智能体升级-验收与后续接入-20261015.md)。这些记录中的通过数只证明所列检查，不证明意图理解准确率、客户转化率或生产容量。

## 三、目标链路

```text
可信渠道消息 + 当前对象/需求状态 + 有界历史 + 已授权知识证据
    ↓
受控理解：多意图、对象归属、陈述性质、候选字段变更、澄清需求
    ↓
服务端验证：结构、字段权限、原话证据、单位、否定/假设、版本、冲突
    ↓
生成本轮拟生效状态与回答；核对二者一致性
    ↓
提交前再查租约、人工状态、企业/渠道、知识版本、需求状态版本
    ↓
事务提交状态变更/审计与验证后消息 → 页面摘要、推荐、人工交接
```

「理解」是逻辑层次，不代表必须额外增加一次模型请求。普通咨询优先用一次结构化模型调用联合返回理解结果、状态变更候选和回答；检索可先依据当前消息与已确认对象召回候选。若本轮更正改变了检索对象，旧证据不再适用，应澄清或受控补查，不能为维持一次调用强行答复。实时工具、多轮工具规划不属于普通路径的默认动作。

模型只提出变更建议。服务端是租户身份、状态版本、字段权限、来源授权和实际动作的权威，不能由租户上传文档或提示词替代。

## 四、需求状态与画像设计

### 4.1 三层分开

- **当前消息理解**：本句问什么、在更正什么、有无多个意图、是否假设/否定/引用他人说法。
- **本次需求状态**：当前项目/商品、目标、限制、预算、期望时间、偏好、待澄清项、已问及已答信息。
- **客户长期记忆**：本轮不默认建设。匿名会话 ID 不是跨渠道客户身份，本次预算不是永久购买力标签。

### 4.2 对象和字段

共同范围至少为 `tenant + conversation + subject`；subject 表示本次官网项目、某个商品或某笔业务对象。新话题可切换活动对象，旧需求保留在原对象下，不能任意继承或全删。没有足够依据时先澄清对象。

字段候选结构：

| 字段 | 含义 |
|---|---|
| key / typed_value | 受控字段标识及数字、区间、枚举或文本值 |
| unit / currency / value_kind | 单位、币种；目标值/上限/区间等语义。币种不明时沿用有依据的会话币种或澄清，不随意推断 |
| status | 用户已明确、暂定、待澄清、冲突、已撤销、已被替代 |
| assertion_type | 用户需求、假设、否定、第三方报价、企业事实等；只允许适用类型进入需求状态 |
| evidence | 访客原消息编号、序号、可校验原文片段/位置；必要时关联上次提问以解释省略 |
| subject_id / state_version | 所属对象和需求版本 |
| supersedes / changed_at | 被替代的字段版本与时间；保留可审计变更，不覆盖证据历史 |

「用户已明确需求」不等于企业确认价格、库存、合同或交期。预算、报价、成交金额和订单金额必须有不同字段与来源。

### 4.3 更新规则

- 支持新增、明确更正、撤销、不变和待澄清；模型输出采用允许列表，禁止任意键写库。
- 新的明确更正替代同对象旧值。暂定新值可成为当前工作假设，但摘要与回答必须标注暂定，旧值不能继续以确定需求出现。
- 区间保存上下界；「不超过五千」保存上限，不能压成无条件精确值；未知不能写成 0。
- 「如果只有五千呢」首先是方案假设，不自动覆盖实际预算；可以分析该假设，必要时确认是否实际调整。
- 「那就五千吧」只有在上文确实在询问本对象预算时才能关联；依据同时包含原提问和本次回答。
- 「不是五千，是八千」需识别否定及目标字段；多个可能对象时澄清，不机械采用最后出现的数字。
- 拆分新项目/不同产品的条件，禁止把官网预算用于 CRM、把商品售价当客户预算。
- 不从助手陈述、检索文档、他人消息或模型推测提取为本人的已确认需求。群聊必须保持发言者及权限范围。
- 模型自报置信度仅供诊断。证据存在、归属正确、语义可支持且通过确定性校验，才允许生效。

示例期望：用户说「预算可能只有5000元了，可以先简单一点，后面再增加功能吗」后，当前官网预算=5000元/暂定，原10000元=已被替代，实施偏好=分阶段，期望两周=保留为用户目标。本句至少同时包含预算更正与分阶段咨询，不承诺5000元一定能交付。

## 五、结构化理解与回答策略

### 5.1 理解契约

输出契约至少包含 `intents[]`、`subject_reference`、`state_delta[]`、`clarification` 和 `answer`；使用现有各协议的能力适配，不能假设所有兼容接口都支持原生 JSON Schema。服务端统一做严格结构验证，格式不支持时返回受控结果，不取消校验。

普通意图包含咨询、比较、需求补充、更正、否定、取消、条件假设、投诉、转人工、结束。业务模板可增加允许的分类；具体写入、转人工和业务工具执行规则仍由服务端控制。

### 5.2 联动要求

- 回答、侧栏、推荐和人工摘要读取同一状态版本；回答同时携带所依据的版本，防止生成后摘要已经变更。
- 回答可自然解释、给出一般规划建议，不要求每句话都存在知识库；企业事实、价格、效果和交付承诺必须有当前有效依据或获授权工具结果。
- 每轮优先回答当前问题，再确认必要变更，只追问一个最影响下一步的问题；不为了填满画像强制收集信息。
- 已问且已答的事项不重复追问；模糊回答和未回答分开记录。明确更正不能变成重新从头做一轮咨询。
- 意图识别到「转人工」不等于可以绕过现有接待授权；沿用已实现的创建、等候、接管与原平台能力限制。
- 模型格式或回答不合格时，可仅提交独立验证通过的状态变更，但对客回复必须基于最终实际提交的状态重新构建；任何不确定候选不得偷偷标为已确认。状态/消息采用同一事务或明确的幂等提交边界，禁止页面看到互相矛盾的版本。

### 5.3 知识与业务数据的边界

继续保持企业公开知识的版本、渠道、受众、撤回、有效期、冲突审批与投递前复核。不能为提高转化放宽事实依据，也不能把本次客户预算写进共享企业知识库。

订单、合同、报表属于业务/内部数据；上传成功不等于允许对所有客户回答。预留业务对象引用与工具接口，实际查询需可信客户身份与对象归属授权。本轮不自动把订单资料转成公开 FAQ。

## 六、SaaS 与多渠道要求

- 提供版本化基础 Schema：对象、需求、意图、状态、证据；标梵预算/交期/分阶段等为一个业务模板。
- 后台为管理员提供受控字段与模板配置：名称、类型、选项、是否可选、显示名称、敏感级别和适用范围。必填只用于明确业务动作，不得强迫用户回答所有字段。
- 配置有版本、允许列表、字段数量/长度上限；不允许上传 Python/JS/SQL 或通过资料内容注册工具。字段删除/更名保留历史解释，不丢原数据。
- 网站 JS SDK、微信/企微/钉钉适配器继续调用同一理解与状态服务，不各写一套画像规则；本轮不修改现有平台认证协议。
- 模型、模板、画像和日志均按租户隔离；模型调用密钥仍由本企业管理员独立配置。暂不合并未经验证的跨渠道身份，不复用其他企业密钥。
- 页面展示暂定、区间、上限、待确认和已撤销状态；内部诊断供授权工作人员查看，不向客户展示提示词或后台推理记录。

## 七、速度、成本与故障约束

以下为下一轮目标，不是已达到的承诺：

| 路径 | 目标及统计要求 |
|---|---|
| 纯问候/精确审核 FAQ | 有效完整回答 P95≤2秒；不因新增画像层强制调用 LLM |
| 普通语义理解+回答 | 健康模型条件下完整答案 P50≤2秒、P95≤4秒；先与当前版同题同负载对照 |
| 应用自身空闲排队 | P95≤100ms；已验证消息提交至页面 P95≤200ms |
| 失败/异常 | 记录故障类型和全链路等待；沿用现有故障保护，不能等待主模型耗尽后再无限重试 |
| 成本 | 普通轮次目标一次模型请求；记录实际调用次数、输入输出、估算/供应商计费差异，不预设真实费用下降比例 |

保留任务唤醒、SSE 续接、连接复用和标准快答。不能把「收到/正在分析」计为有效回答，不能把仅命中 FAQ 的速度报告为语义理解速度。

FAQ 只在消息确实是独立标准问题且不含未处理的需求变更时使用。混合提问需处理变更，不能只用快答丢弃需求；歧义省略不得强套标准答案。

现有真实模型生成此前出现超时，实施前须重新诊断并记录状态。可先完成隔离测试、状态层和故障验证；真实通道不可用时不得宣布「语义质量及两秒目标已验收」，不得静默换模型或共享密钥。备用通道仅在企业具备并配置可用凭据后另行接入。

## 八、实施分批与交付门槛

### 第一批：冻结基线、契约与题集

交付：当前链路图、字段状态 Schema、结构化输出契约、对象切换/更正/撤销决策表、多轮验收集及评分说明。保存当前应用和数据备份，锁定模型、提示、知识、模板版本，跑相同基线。

题集至少120段多轮对话、合计不少于600条用户消息，覆盖标梵销售与通用商品/售后合成场景。按完整对话分训练/调优集与保留验收集，不把同一对话的改写分到两边。标注期望意图、字段状态、证据、是否应澄清和不得承诺项；含假设、否定、区间、含糊、插话、话题切换、多对象、混合意图、人工接管及故障。

### 第二批：统一状态层，先以影子方式运行

交付：需求状态、事件/版本、证据与幂等更新服务；租户配置入口骨架；旧 profile 兼容投影。只在独立测试库验证迁移，再开启标梵影子计算，结果不直接影响客户。

旧资料不自动补为「已确认」。可引用原消息的旧字段先标明来源与兼容状态，不批量回填模型猜测。历史回放必须限定本轮消息序号；不得让早期任务读到后来一轮的画像。重复回调、重试、迟到模型结果、Worker 重启都不能重复变更或覆盖新版本。

### 第三批：接入语义理解与一致性校验

交付：可替换理解器（模型实现/保守规则兜底）、结构验证、证据绑定、类型与单位校验、多意图、对象消歧、冲突/暂定规则、单调用联合输出路径。规则用于可解释兜底和约束，不作为开放语言理解的唯一主体。

异常时允许「此轮无法确认变更」，明确标记待澄清，不把旧值伪装成最新确定需求。新状态和对客文本必须通过一致性检查，失败有原因码及回退路径。

### 第四批：页面、推荐与人工联动

交付：摘要状态显示、同版本推荐、人工摘要与原话追溯、必要的用户纠正入口、后台受控字段配置。转人工、预约及五分钟联系服务流程保持；画像更新不重置 deadline，不代替真实人工联系。

先验证标梵，再用另一独立合成企业验证通用商品/售后模板、租户配置及数据隔离；不依赖海信真实密钥，不为测试复制标梵凭据。

### 第五批：同题对照、灰度与回退

交付：正确性/延迟/故障/成本报告、浏览器真实验收、灰度开关和回退手册。按企业开关从影子到小范围启用，不直接全量覆盖内网同事正在使用的会话。

上线门槛包括数据迁移可用、核心回归通过、保留题集达标、真实模型验收和回退可用。未通过真实模型门槛时只交付受控试验版，不能标为完成上线。

回退采用企业开关关闭新理解器，保留增量状态表和已验证的变更历史，不直接降级/删列或让旧规则覆盖新状态。兼容投影必须保留暂定/区间语义，旧消费者无法表示时展示待确认，不伪装为确定值。回退后继续遵守人工接管、权限、知识撤回及原 SLA，需在隔离环境演练。

## 九、验收指标与口径

以下阈值为本方案初始验收目标，需在第一批冻结评分口径；不是现有实测值。逐类列分母，不能只报告平均数。

| 指标 | 口径与初始目标 |
|---|---|
| 多意图识别 | 报告每类 precision/recall 与整体 micro-F1；整体 F1≥0.90，变更/撤销/人工意图召回各≥0.95 |
| 关键状态更新 | 预算、时间、目标对象的值+单位+状态+归属均正确才算正确；适用轮次正确率≥98% |
| 错误覆盖 | 不应变更的轮次被改动的比例≤1%；对否定/假设/不同对象单列 |
| 回答与状态一致 | 适用轮次≥98%；列出残留旧值、把暂定说成确定、错误继承的具体例子 |
| 证据完整性 | 生效字段能回到授权的访客消息及片段；所有验收生效变更必须具备有效依据 |
| 硬性边界 | 验收集中跨租户/内部泄露、未经授权承诺、人工接管后 AI 投递、重复变更、旧任务覆盖新状态均不得出现；零观测不代表未来绝对零风险 |
| 回答可用性 | 分清回答当前问题、少重复追问、自然程度；人工评分1–5，目标平均≥4且无重大事实错误，附评分依据 |
| 速度与故障 | 按FAQ、真实模型成功、故障、澄清分别给P50/P95、成功/失败数；模拟结果独列，不剔除慢请求美化整体结果 |

模型语义评测须人工复核代表性样本与所有重大失败，不能完全交给另一个模型打分。小样本类别分母不足20时补充样本再判定，不能以一两条通过宣称95%。

并发验收先从10个并发普通会话开始，记录冷/热状态、队列、用量和数据库负载，再按公司目标扩展；该数是起始测试场景，不是已证明的产品承载量。模型不可用时无法完成真实语义负载验收。

## 十、边界与不可突破的约束

### 本轮做什么

意图理解、会话内需求画像、统一状态、回答/摘要/推荐/人工交接联动、受控企业模板、评测和故障观测，以及必要的增量迁移和小范围界面调整。

### 本轮不做什么

- 不更换 React/TypeScript、FastAPI、SQLAlchemy/PostgreSQL；不重写整个系统或另建一套并行客服。
- 不扩建复杂智能体集群、不同时叠加图谱/搜索数据库/多向量库；当前全量扫描的规模化问题独立评估。
- 不把知识更新、订单接入、跨渠道身份合并、公网部署、收费订阅和真实平台授权一并当成本轮交付。
- 不自动签合同、改订单、报确定价格、承诺交期/效果，不执行未实现的业务动作。
- 不默认跨会话长期记忆，不推断性别、收入、健康等敏感画像；不保存隐藏思维过程作为诊断。
- 不重新设计全站 UI，不删除原功能或历史消息，不重置企业账号、密码、API密钥和工作时间。

### 工程与数据硬约束

1. 隔离：租户、受众、渠道、会话、对象权限贯穿解析/检索/模型/缓存/日志/提交；仅凭模型提供的 ID 不授予权限。
2. 可靠：沿用持久任务、租约、幂等、消息顺序；人工接管、撤回、停用与权限改变在投递前复查。
3. 一致：状态变更与消息绑定版本；临界提交校验 revision。冲突时重读、重新核验或抑制，不能最后写入者随意胜出。
4. 兼容：对外 API/JS SDK 尽量增量兼容；旧 profile 保留过渡投影，内部/外部消费者迁移清单明确后再退役旧字段。
5. 迁移：测试库先验证、上线前备份；旧数据按证据迁移，不生成虚假事实；不在试点库执行破坏性测试。
6. 安全：凭据服务端加密；脱敏日志、有限保留与删除同步；撤销/删除不能被记忆重放或缓存重新复活。
7. 成本：默认复用已配置模型与已有数据库，不静默新增付费调用供应商；后台可控限额，无无界历史、无限重试或全量同步推理。
8. 部署：当前只做内网版本。公网 HTTPS、平台回调、真实平台账号权限是后续外部条件，不伪造验收。临时供应商故障不能通过关闭来源/权限核验来解决。

## 十一、后续开发执行说明

接手者先阅读本方案及三份基线验收文档，以当前代码为准。按五批实施，每批列出修改、迁移、回归结果、真实/模拟边界与尚存问题；未达门槛不得跳到全量启用。

优先改造点是 `mvp/service.py`、`server/requirements.py`、`server/dialogue_policy.py`、`mvp/worker.py`、`mvp/reception.py` 与 `web/mvp/ui.tsx`；新增状态服务和迁移遵循现有目录，不把实现继续堆进单个正则文件。

理解器接口应允许后续替换模型；业务状态更新、证据验证和权限校验不能埋在供应商提示词内。先落地状态契约与题集，再接模型，最后切换消费者。

本方案不要求现在重新申请海信 API、购买服务器或迁移同事数据库。真实模型不健康时继续完成独立实现及隔离验证，保留真实质量验收未完成状态。推送GitHub、修改同事仓库、上线公网另按用户实际授权执行。
