# 两秒响应：系统评估与优化方案

评估日期：2026-10-15。本轮只读代码、统计已有调用记录、核对官方资料；没有改动程序、企业配置或发起新的付费模型请求。

## 结论与目标

恢复多数普通问题约2秒的体验有历史依据。优先处理模型生成通道异常，以及本系统已有的任务轮询和页面消息投递等待；继续削减十几毫秒的检索不可能弥补20秒模型超时。

建议分开验收三项：

- **普通问候、经审核的标准FAQ**：目标P95在2秒内显示完整、有效答案。
- **需要模型分析的问题**：模型通道健康时，目标P50完整答案2秒内、P95完整答案4秒内。复杂题另设完成时间，首个有效内容与完整答案分别统计。
- **模型故障时**：已知故障尽快降级，普通问题目标2秒内给出有用且安全的回答；不把“收到、正在思考”算回答成功，不把故障兜底算LLM成功。

如果要求所有问题严格2秒截止，可以设置约1.5秒模型预算，剩余时间走安全兜底，但会提高正常慢请求被截断的比例。这是速度和模型生成成功率的产品取舍，不能宣称回答质量完全不受影响。建议先实现上述分层目标，再用实际数据决定硬截止时间。

## 二、系统自身发现的等待

### 1. 任务每秒轮询

`mvp/worker.py` 主循环最后 `STOP.wait(1)`。任务在API提交后，需要等待worker下一轮获取租约，历史排队中位约0.75秒。主循环还处理心跳、SLA、通知和来源同步调度。

优化：消息事务提交后用PostgreSQL通知唤醒AI调度，保持数据库持久任务和租约为权威。通知只携带不含客户正文的标识，worker仍按服务端租户范围领取任务；连接恢复和漏通知由定时扫描兜底。可先小步改成提交唤醒+低频兜底，不引入新的Redis服务。

目标：空闲时任务提交到开始处理的P95不超过100毫秒。该数字是待验证目标。

### 2. 有消息通道，但仍是两秒检查

`mvp/app.py` 的客户SSE接口每2秒检查消息，循环25次后结束。`web/mvp/main.tsx` 的客户连接函数读到流结束会退出，没有同一会话下的持续重连机制；另有4秒轮询兜底。理论上，一次消息更新还可能增加接近2秒等待；流结束后可能增加接近4秒。不是每条请求都固定叠加这些最大值。

优化：修复断线/正常结束后的重连，使用已收到的消息序号续接、去重，并在会话变更/退出时取消旧连接。服务端在消息提交后唤醒消息分发，减少定时查询等待；保持断线兜底。不能简单让每个访客每100毫秒查数据库，以免放大负载。

目标：已验证答案落库到浏览器渲染的P95不超过200毫秒，覆盖页面打开超过60秒后的会话。

### 3. 每次重新创建模型HTTP连接

`server/model_gateway.py:complete()` 每次新建并关闭HTTP客户端，无法复用连接。可以按受控租户/服务端配置复用连接，保留TLS校验、地址检查与租户凭据隔离，设置连接池上限和关闭策略。认证信息应随请求设置，禁止共享客户端默认头、Cookie或日志泄露凭据。

该项可能减少连接建立开销，具体收益需对照测量；不能预先声称固定节约数百毫秒，更无法解决供应商排队。

### 4. 整段答案校验后展示

当前虽然用HTTP流读取响应字节，但没有向模型发送 `stream:true`；会等完整JSON返回，再进行引用、数字、权限和资料版本核验。

第一阶段保留完整验证，把“验证完成后的投递”变快。直接把未验证token显示给客户有错误报价、错误承诺、撤回资料泄露风险，不能作为最快上线方案。若后续做真正token流式，需要单独设计可提前展示的内容与取消机制，分别验收首个有效内容和完整答案。

## 三、方案优先级

| 顺序 | 方案 | 收益与目标 | 成本 | 主要风险/条件 |
|---|---|---|---|---|
| P0 | 恢复健康模型通道，细化HTTP状态、首内容、总时长诊断；支持企业独立备用配置 | 恢复真实LLM生成成功率，是接近过去1–2秒生成的关键 | 中；备用需要企业已有可用配置或另行授权 | 同一供应商的另一个模型不一定提供故障隔离；不能自动共享其他租户密钥 |
| P0 | 修复SSE续接和提交后的消息推送 | 避免已生成答案还在等待2–4秒显示 | 中 | 断线重连、消息重复/乱序、权限过期、旧会话串入需测试 |
| P1 | AI任务提交唤醒，保留租约和兜底扫描 | 排队目标P95<=100毫秒 | 中 | 不漏任务；重启、通知丢失、人工接管仍安全 |
| P1 | 消费者可用FAQ快路径 | 问候/稳定标准问题目标P95<=2秒 | 中 | 必须使用人工审核的对客答案；不原样输出内部操作指引，不对宽泛需求强行套某型号 |
| P2 | 连接复用、精简重复提示词、按题控制输出长度 | 减少正常模型请求开销，收益待测 | 低到中 | 保留用户最新预算/时间、话题、来源和服务边界；避免JSON截断 |
| P2 | 授权范围内缓存 | 重复公共问题减少重复模型等待 | 中 | 企业/渠道/版本/有效期/回答策略隔离，命中后再核验授权；个人订单和个性化答案不共享 |
| 后续 | 真正LLM流式输出 | 可能改善较长答案的首内容时间 | 中到高 | 不改善模型开始生成前的长等待；需要额外内容安全设计 |
| 暂缓 | 换数据库、叠加图谱、拆更多智能体 | 当前标梵检索仅十几毫秒，预期收益低 | 高 | 增加依赖与故障点；没有本轮瓶颈证据 |

## 四、FAQ和缓存边界

适合快路径：问候、已审核公司介绍、明确的资料准备清单、具有精确型号与适用条件的参数问答。

不适合直接快答：客户组合需求的个性化推荐、可否按预算成交、交付保证、实时库存和订单状态、矛盾活动时间、需人工核实的信息。

缓存只共享本企业公开标准问题，键包含受众/渠道、规范化问题、资料版本/授权状态、答案策略等；每次命中仍复核当前来源和有效期。不得用相似问题的答案替代新的预算、型号、地域或时间条件。旧答案在资料撤回、替换、过期后停止使用。

## 五、生成链路的精简方式

1. 保留现有“已发布、对客、租户/渠道范围、精确型号、投递前复核、人工接管”规则。
2. 普通咨询保留3–4条真正相关证据。明确事实问答可减少到1–2条，比较问题保留必要双方资料，不机械截取。
3. system提示词去重；当前抽样约2333字符，存在精简空间，但不是20秒故障等待的主要原因。
4. 历史从最多40条、约12000字符，演进为最近几轮+带原消息依据的明确需求。最新预算、时间、否定条件和已回答问题不能丢。
5. 普通短答试验384 tokens，复杂答案保留800或适用上限；只降低max_tokens不保证提速，也可能截断JSON。以真实输出、截断率和内容评分决定。
6. 连接复用与同一题集对照后再决定是否调整模型。当前已经关闭业务深度思考，不把重复关闭当作新增收益。

## 六、两秒设计预算

以下是健康模型、普通问题的设计预算，不是实测承诺；各阶段时延分布的P95不能简单相加当作全链路P95。

| 阶段 | 目标预算 |
|---|---:|
| 接收与调度 | 100毫秒 |
| 检索与上下文组织 | 100毫秒 |
| 模型正常生成 | 1400毫秒左右 |
| 最终核验与保存 | 100毫秒 |
| 浏览器收到并显示 | 200毫秒 |
| 合计参考 | 约1900毫秒 |

模型无输出时，前述本地优化不能独自把完整LLM答案变成2秒。需要健康备用通道，或用明确标注的有效知识回答。备用请求必须有整体截止时间、单次恢复限制、用量预留与幂等投递；不可等待主模型8秒后才再花8秒等待备用。

## 七、建议执行顺序与验收

第一批：先修SSE重连与消息即时投递、任务唤醒，同时细化模型异常原因。保留现有模型配置和服务边界。

第二批：审核常见对客FAQ，加入快路径；然后做连接复用、提示去重和动态输出长度。模型异常期间统计降级路径，不假装恢复正常。

第三批：企业已有独立可用备用凭据时接入备用通道；没有则如实保留单供应商故障边界。无需为这一轮本地改进重新申请密钥。

验收必须记录：

- 从点击发送到首个**有效内容**、完整答案的P50/P95，含排队和浏览器显示。
- LLM成功率、故障降级率、FAQ命中率及各类错误；不能只统计成功调用，也不能只统计缓存命中。
- 相同题集、相近负载的前后对照；至少200条合成回放，包含短答、复杂追问、精确型号、超时、长开页面、断网恢复和人工接管。
- 对客回答正确性与自然程度；跨租户/内部资料泄露、伪造报价/承诺、过期引用均不得出现。
- 明确模型健康、模型故障、缓存命中和冷启动各组，不能混在一起报告“平均2秒”。
